# business-methodology

一个「沉淀业务方法论」的 Agent Skill：把运营 / 产品 / 开发的工作笔记、复盘、分析报告，抽象成**结构化、可检索、可复用的方法论卡片**（小而多的 Markdown 文件）。目标是让一次性的工作产出，变成团队下次能直接调用的「规则库」。

## 它产出什么

- 一张张独立的**方法论卡片**（一条规则一张卡），存放在 `方法论库/{角色}/` 下。
- 一个总索引 `方法论库/INDEX.md`，按角色汇总全部卡片，方便检索。
- 卡片带 frontmatter 标签（角色 / 业务域 / 方法论类型），可机器检索。

## 目录结构

```
business-methodology/
├── SKILL.md                  # skill 主指令
├── README.md                 # 本文件
├── assets/                   # 三套角色卡片模板
│   ├── card-template-运营.md
│   ├── card-template-产品.md
│   └── card-template-开发.md
└── references/
    └── tag-taxonomy.md       # 业务域与方法论类型的标签体系
```

## 怎么用（填空输入）

每次使用，按下面四个字段**填空**提交即可：

```
【文件】     要沉淀的文件路径（必填）
【角色】     运营 / 产品 / 开发（必填，三选一）
【业务内容】 一句话说明这条材料是关于什么的（必填）
【来源类型】 工作笔记 / 复盘 / 分析报告 / 需求·技术方案 / 实验数据记录 / 会议纪要 / 周报·月报（选填，缺省自动判断）
```

示例：

```
【文件】 C:\docs\2026-10-活动复盘.md
【角色】 运营
【业务内容】 新手期次留提升实验的完整复盘
【来源类型】 复盘
```

## 接受的文件类型

工作笔记、复盘、分析报告、需求 / 技术方案、实验数据记录、会议纪要、周报月报等（`.md` / `.txt` / `.docx` / `.pdf` 均可，能读出文字即可）。

## 什么情况下会被拒绝

- 文件路径不存在、读不了、或类型不支持。
- 【角色】不在「运营 / 产品 / 开发」三选一内。
- 【业务内容】为空。
- 材料是**纯流水账**——只有「发生了什么」，没有判断、结论、或可复用的做法。

被拒绝时会明确说明缺什么；不会为了产出而编造方法论。

## 每张卡片长什么样

每条卡片都必须包含（缺一不产出）：

| 字段 | 作用 |
|---|---|
| **来源** | 由哪条材料沉淀而来，可回溯 |
| **适用边界** | 什么前提才适用、什么情况不适用 |
| **可执行步骤** | 下次照着就能做的动作 / SOP |

外加：标题、适用场景、核心逻辑、判断标准、标签。

三套角色模板侧重点不同：**运营**偏向「策略 / 转化」，**产品**偏向「需求 / 决策」，**开发**偏向「技术方案 / 工程质量」。

## 标签体系

skill 会自动打标签，不用你填。业务域（增长 / 留存 / 转化 / 效率 / 质量 / 协作 / 成本 / 风险）× 方法论类型（决策原则 / 操作SOP / 判断标准 / 模板清单 / 教训反例）。详见 `references/tag-taxonomy.md`。

## 安装

把它作为一个 Agent Skill 安装到你的 agent 里（`SKILL.md` 在根目录，符合通用 skill 约定）。以 DSH 为例，放到 `<dshHome>/skills/business-methodology/`，或项目内 `.dsh/skills/business-methodology/`。

## 设计原则

1. **抽象而非摘要**：提炼「下一次该怎么做」，不是把笔记变短。
2. **不编造**：只沉淀材料里真实存在的规则；查不到就说没有可沉淀的东西。
3. **可复用**：每条卡片必须有来源、边界、可执行步骤，否则不产出。
4. **小而多**：一条规则一张卡，宁可多张卡，不塞成一篇大文档。
