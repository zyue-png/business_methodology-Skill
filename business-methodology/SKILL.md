# 业务方法论沉淀

把零散的工作材料，抽象成「下一次遇到同类问题时该怎么做」的可复用规则。**不是做摘要**，而是做「抽象 + 复用」：卡片写的是规则，不是一次性事件本身。

## 输入清单（填空格式，缺什么先问什么）

- 【文件】要沉淀的文件路径（必填）
- 【角色】运营 / 产品 / 开发（必填，三选一）
- 【业务内容】一句话说明这条材料是关于什么的（必填）
- 【来源类型】工作笔记 / 复盘 / 分析报告 / 需求·技术方案 / 实验数据记录 / 会议纪要 / 周报·月报（选填，缺省自动判断）

## 拒绝规则（先校验，不满足就直接拒绝，不要硬编）

满足以下任一条即**拒绝生成**，并明确说明原因：

1. 【文件】路径不存在、读不了、或类型不支持。
2. 【角色】不在「运营 / 产品 / 开发」三选一内。
3. 【业务内容】为空。
4. 材料是纯流水账：只有「发生了什么」，没有判断、结论、或可复用的做法——没有可沉淀的东西。

拒绝时说明缺什么；不要为了产出而编造方法论。

## 处理流程（顺序不能反）

1. **读材料**：完整读取文件，理解业务问题、事实、判断、结论。
2. **判定可沉淀性**：材料里有没有「可复用的规则 / 判断 / 做法」？没有则按拒绝规则第 4 条拒绝。
3. **抽取方法论点**：识别出 1–N 条独立的方法论（一条规则一张卡，小而多，不要硬塞成一篇大文档）。
4. **抽象**：把「这次具体做了什么」提炼成「下次该怎么做」，去掉仅属于本次的偶然细节。
5. **打标签**：按 `references/tag-taxonomy.md` 自动归类业务域与方法论类型，不向用户索要标签。
6. **按角色模板写卡片**：用 `assets/` 下对应角色的模板。
7. **质量自检**：每条卡片必须有「来源 / 适用边界 / 可执行步骤」，缺一条就不产出该卡。
8. **更新索引**：写入并维护 `方法论库/INDEX.md`。

## 输出：方法论卡片

目录结构（相对工作区根目录）：

```
方法论库/
├── INDEX.md          # 总索引，每次新增卡片后更新
├── 运营/
├── 产品/
└── 开发/
```

卡片命名：`{业务域}-{主题关键词}.md`，例如 `增长-新手期提升次日留存.md`。

卡片字段（frontmatter 元数据 + 正文，完整骨架见 `assets/` 三套模板）：

| 字段 | 必填 | 说明 |
|---|---|---|
| 角色 / 业务域 / 方法论类型 / 标签 / 来源 | ✅ | frontmatter 元数据，用于检索 |
| 标题 | ✅ | 一句可检索的方法论名称 |
| 适用场景 | ✅ | 什么业务问题、什么触发条件 |
| 核心逻辑 | ✅ | 2–4 句讲清「为什么这么做」 |
| 操作步骤 / SOP | ✅ | 可执行步骤（必填三项之一） |
| 判断标准 | ✅ | 何时算成功、何时止损、量化阈值 |
| 适用边界 | ✅ | 什么前提才适用、什么情况不适用（必填三项之一） |
| 来源 | ✅ | 由哪条材料沉淀而来，可回溯（必填三项之一） |

## 分角色沉淀视角

沉淀时按角色聚焦，不要把三类材料套同一套话术：

- **运营** → 聚焦「策略 / 转化」：增长手段、活动玩法、转化漏斗、投放策略、用户分层。
- **产品** → 聚焦「需求 / 决策」：需求优先级、产品决策依据、用户调研结论、MVP 取舍、数据驱动的取舍。
- **开发** → 聚焦「技术方案 / 工程质量」：方案选型、架构决策、性能 / 稳定性 / 质量保障、故障复盘、工程规范。

## 标签自动归类

按 `references/tag-taxonomy.md` 归类。业务域选最贴切的一级类（可多选，最多 3 个）；方法论类型只选一个主类（决策原则 / 操作SOP / 判断标准 / 模板清单 / 教训反例）。不要新增不在表内的类别；确有需要时在卡片里注明「新类别建议」，并沿用最接近的现有类。

## 质量红线

- 每条卡片必须有「来源 / 适用边界 / 可执行步骤」，缺一即不产出该卡。
- 只抽象材料里真实存在的规则，不编造材料没有的结论、数字、案例。
- 区分「这一次的结果」和「下一次的规则」：卡片写规则，不写一次性事件本身。
- 边界必须写清楚：没有前提、没有例外说明的「普适规律」不产出。

## 支持文件

- `assets/card-template-运营.md`、`assets/card-template-产品.md`、`assets/card-template-开发.md`：三套卡片模板。
- `references/tag-taxonomy.md`：业务域与方法论类型的标签体系。
